**SEO 选题分析器。**

大致思路是：输入一个关键词，把我搜到的下拉词、搜索指数、竞品标题等等丢进去。

```Plain Text
然后让 AI 帮我分析：这个词值不值得写？用户到底在搜什么？有哪些长尾关键词？哪个词竞争小？应该先写哪篇？能不能围绕这个词做成一个内容集群？顺便再给我生成标题和文章框架。
```

> **Vibe Coding。**

**让 GPT Pro 负责想，让 Codex 负责干，让GPT\-Image2负责UI。**

# 一、不让 Codex 直接写代码

这应该算是我最近用 AI Coding 最大的一个变化。

以前想到一个东西，我第一反应基本都是：

打开 Codex然后：帮我做一个 XXX。但是往往后期就会越来越乱，难以维护！

所以这一次，我决定反过来。

**先不写代码。**

先把产品想明白。

而这个工作，我准备全部交给 **GPT Pro**。

我的分工非常简单：

> 我负责提出需求和做最终决定。
>  GPT\-5\.6 Pro 负责产品设计、需求拆解和验收。
>  Codex 负责真正开发、运行、测试和修改。
> 
> 

所以所谓的：

**GPT Pro 指挥 Codex。**

并不是说 GPT\-5\.6 Pro会隔空操作 Codex。

中间真正传递信息的是：

**PRD、开发计划、验收标准、测试结果和审查报告。**

我只是负责在中间做最后的决策。

整个流程大概是这样：

![image\.png](/images/vibe-coding-practice/image-14.png)

而且我去翻了一下 GPT 最新的官方 Prompting 建议，方向其实也差不多：比起给模型塞一大堆机械步骤，更重要的是告诉它**目标、上下文、约束、完成标准和最终想得到什么结果**。

# 二、第一步：我先让 GPT Pro 来问我

我只告诉它，我想做什么。

我给 GPT\-5\.6 Pro 的第一条指令是：

> 我准备通过 Vibe Coding 从 0 开发一个「SEO 选题分析器」。
> 
> 你先作为这个产品的产品经理，帮我把需求彻底弄清楚。
> 
> 我的初始想法是：
> 
> 用户输入一个核心关键词，再输入或者导入相关的搜索数据，例如搜索下拉词、相关关键词、搜索指数、竞品标题、竞品阅读数据等。
> 
> 系统利用 AI 对这些数据进行分析，最后输出：
> 
> - 搜索意图 
> 
> - 长尾关键词 
> 
> - 选题优先级 
> 
> - 竞争程度 
> 
> - 推荐标题 
> 
> - 单篇文章大纲 
> 
> 未来希望能够支持微信公众号搜一搜、百度、Google、小红书、知乎、B站等不同平台。
> 
> AI 模型不能写死，希望未来能够切换 OpenAI、DeepSeek 以及其他兼容 API。
> 
> 你现在的任务不是帮我设计产品，而是先不断向我提问。
> 
> 找出这个需求里所有还没有定义清楚的问题。
> 
> 每轮最多问我 5 个最关键的问题。
> 
> 等你认为产品边界已经足够清晰，再停止提问。
> 
> 

![image\.png](/images/vibe-coding-practice/image-6.png)

这一轮我特别加了一句话：

**不要急着帮我设计。**

因为我发现 AI 有一个很大的问题。

它很容易立刻给你：数据库设计、技术栈、页面结构、商业模式……

看起来特别完整。但是这些东西很可能根本不是你真正想要的。

所以这一轮，我只让它问。

![image\.png](/images/vibe-coding-practice/image-3.png)

然后我就按照它的问题，一轮一轮回答。

最后慢慢把这个产品确定下来。

![image\.png](/images/vibe-coding-practice/image-5.png)

# 三、先把大而全砍掉

一开始我脑子里的 SEO 选题分析器其实非常大。

甚至我第一反应是：能不能让它自动去搜？自动抓微信搜一搜？自动生成文章？自动发布？

……

如果全部做，那最后大概率又会变成一个无限开发的项目。

所以问完几轮之后，我又给 Pro 加了一条指令：

> 现在基于我们前面的全部对话，帮我重新审查一次需求。
> 
> 重点不是增加功能，而是删功能。
> 
> 请把所有需求分成：
> 
> 第一版必须有 ；第二阶段再做 ；暂时完全不要做 
> 
> 判断标准只有一个：
> 
> 第一版必须形成一个完整闭环：用户能够输入真实 SEO 数据 → AI 完成分析 → 用户得到能够直接用于选题的结果。
> 
> 任何不能直接强化这个闭环的功能，第一版都尽量删除。
> 
> 最后给我一个最小可用版本 MVP。
> 
> 

这一轮非常重要。

因为我真正要的是

> **AI 能不能把一堆杂乱的 SEO 数据，变成我真正能用的选题建议。**
> 
> 

所以第一版最后被我砍成了几个东西。

# 四、SEO 选题分析器第一版到底做什么？

经过反复的删、改

第一版我准备只保留这些。

输入一个大词 →

# 五、需求差不多之后，我才让 Pro 写 PRD

前面几轮全部聊完之后。

我才开始让 GPT\-5\.6 Pro 真正输出东西。

我的下一条指令是：

> 现在需求已经基本明确。
> 
> 请基于前面的所有对话，为「SEO 选题分析器」生成第一版正式 PRD。
> 
> 这份 PRD 是直接交给 Codex 开发的，所以不要写成泛泛的产品分析文章。
> 
> 尽量从结果描述，而不是替开发者规定每一行应该怎么写。
> 
> 最后直接输出一个可以保存为 `PRD.md` 的正式版本。
> 
> 



![image\.png](/images/vibe-coding-practice/image-12.png)

这一点我现在越来越喜欢。

先把聊天变成文档，任何再给codex。

PRD 一旦生成之后：

这一版要做什么不做什么，做到什么程度算完成。

全部固定下来了！

# 六、然后再单独让 GPT Image V2 设计页面

这一步我也没有交给 Codex 自由发挥。

因为 AI Coding 最容易出现的一个问题就是：

功能能用，但是界面一眼 AI。

所以我又单独开了一轮：

> 下面开始设计 SEO 选题分析器的 UI。
> 
> 我希望它首先是一个「生产力工具」，而不是 AI 官网。
> 
> 整体以白色和浅色为主。
> 
> 不要大面积蓝紫渐变。
> 
> 不要为了体现 AI 而到处做发光效果。
> 
> 不要过度圆角。
> 
> 信息密度可以稍微高一点。
> 
> 核心感觉应该接近：
> 
> 数据分析工具 \+ SEO 工作台。
> 
> 使用流程必须非常明显：
> 
> 创建项目 → 输入数据 → AI 分析 → 查看选题 → 深入某个选题。
> 
> 你需要一次性把这个系统所需要的所有页面都设计出来，可能是9宫格，也可能是其他
> 
> 最后整理成可以直接交给 Codex 的 UI 规范。
> 
> 

![image\.png](/images/vibe-coding-practice/image-7.png)

这里其实 GPT\-5\.6 Pro 挺适合干这个。

让 Pro 先决定页面应该长什么样。

![image\.png](/images/vibe-coding-practice/image-19.png)

再让 Codex 去实现。

比一句：做得高级一点靠谱多了！

# 七、到这里，我才第一次打开 Codex

前面的时间，其实一行代码都没有写。

现在我手上已经有了：

- `PRD.md`

- UI 规范 

- MVP 边界 

- 验收标准 

接下来才是 Codex。

先让它读。我给 Codex：

> 请完整读取当前项目以及 `PRD.md`。
> 
> 现在不要修改任何代码。
> 
> 先理解我要开发的 SEO 选题分析器。
> 
> 检查当前开发环境和项目状态，然后输出一份开发计划。
> 
> 开发计划需要明确：
> 
> - 准备采用的整体架构 
> 
> - 项目目录 
> 
> - 每一个开发阶段 
> 
> - 每个阶段会完成什么 
> 
> - 每个阶段对应的验收方法 
> 
> - 可能存在的风险 
> 
> - 哪些地方需要我确认 
> 
> 把最终计划写入 `PLAN.md`。
> 
> 在我确认计划之前，不要开始正式开发。
> 
>

我先让 GPT\-5\.6 Pro 当产品经理。

# 十一、最后把审查报告重新交给 Codex

然后非常简单。

把 `REVIEW.md` 放回项目。

告诉 Codex：

> 完整读取 `REVIEW.md`。
> 
> 这一次只处理 Blocker 和 Major。
> 
> 不要顺手增加新功能。
> 
> 每修复一个问题，都需要重新运行对应测试。
> 
> 同时检查修改是否破坏已经通过的旧功能。
> 
> 全部完成后重新执行完整回归测试，并更新验收结果。
> 
>

# 十二、做到这里，我对 Vibe Coding 又有了一个新的理解

项目稍微大一点之后，真正重要的已经不是：**怎么让 AI 多写代码。**

而是：**怎么让 AI 少走弯路。**

所以我现在这一套流程，核心其实只有几个东西：

先把需求聊清楚。再确定什么不做。把完成标准写下来。

让 Codex 执行。让 Codex 自己证明自己完成了。

再换一个 AI 独立审查。

最后不断闭环。

如果非要把它压缩成一句话：

> **GPT Pro 决定做成什么样，Codex负责把它真正做出来。**
> 
> 

我自己负责：

**在关键节点做决定。**

# 十三、Vibe Coding 到底适不适合小白？

我反而觉得现在很适合。

因为以前不会代码的人最大的障碍是不知道怎么写。

现在这个障碍已经小很多了。

但是新的障碍变成了**不知道自己要什么。**

你连产品要解决谁的问题都没想明白。

再强的 Codex 也只能帮你生产一堆错误。

**先找一个你自己真的有需求的小东西。**

然后按照我这一篇的流程：

**想法。需求。MVP。PRD。Codex。测试。验收。**

真正从头跑一次。

跑完第一个之后，很多东西自然就懂了。

![image\.png](/images/vibe-coding-practice/image-11.png)

# 最后

从 0 做一个产品，配置好模型、让页面跑起来，其实只是第一步。

长期上下文怎么管理；AGENTS\.md 怎么写；Skill 怎么做；项目越来越大以后怎么让 Codex 不乱；一个对话不够了怎么接着开发；怎么让多个 AI 一起协作。怎么测试。怎么部署。

这些我最近也一直在实操。

我都会慢慢写。
